# Отчет по нагрузочному тестированию и оптимизации базы данных

## 1. Обзор проекта
Основная сущность: Пользователи (user) — центральная сущность приложения для знакомств, от которой зависят все остальные функции (лайки, сообщения, матчи).

Тестируемые API эндпоинты:
*   POST /api/register — регистрация нового пользователя (создание)
*   POST /api/login — аутентификация пользователя (чтение)

## 4. Сравнительный анализ и выявленные проблемы

| Показатель | Базовый тест (Localhost) | Текущий тест (Remote) | Статус |
| :--- | :--- | :--- | :--- |
| RPS | ~180 | ~12 | 🔴 Критическое падение |
| Latency (Avg) | ~330 мс | 1.85 сек / 0 мс (timeout) | 🔴 Недопустимо высокая |
| Ошибки (Timeout) | 0 | ~100% (717-725) | 🔴 Сервис не справляется |

Критические проблемы:
1.  Тотальные таймауты: Почти 100% запросов завершились по таймауту. Система не успевает обрабатывать входящие соединения.
2.  Деградация RPS: Производительность упала в 15 раз по сравнению с локальными тестами.
3.  Нестабильность соединения: Высокое стандартное отклонение (Stdev) для запросов в секунду.

## 5. План оптимизации

### Шаг 1: Анализ базы данных (EXPLAIN)
Необходимо проанализировать запросы через ANALYZE, чтобы понять причины задержек:
*   Регистрация: INSERT INTO "user" ... RETURNING id, created_at, updated_at, last_active;
*   Логин: SELECT id, password, email, ... FROM "user" WHERE email = ...;

### Шаг 2: Стратегия улучшения производительности БД

#### 1. Индексы (Высокий приоритет)
*   Добавить покрывающие индексы (covering indexes).
*   Создать составные индексы для сложных условий WHERE.
*   Добавить BRIN-индексы для полей дат (created_at, updated_at).
*   Удалить неиспользуемые индексы, замедляющие INSERT.

#### 2. Настройки PostgreSQL
*   Увеличить shared_buffers (до 25-40% от RAM).
*   Настроить work_mem и maintenance_work_mem.
*   Оптимизировать random_page_cost под SSD (1.1–1.5).
*   Включить pg_stat_statements для постоянного мониторинга.

#### 3. Оптимизация схемы и запросов
*   Использование Prepared Statements для исключения повторного парсинга SQL.
*   Рассмотреть замену UUID на BIGSERIAL для первичных ключей (улучшает локальность данных).
*   Устранение проблемы N+1 на уровне приложения.

#### 4. Архитектурные улучшения
*   PgBouncer: Внедрение пула соединений для управления 1000+ конкурентными подключениями.
*   Кэширование: Использование Redis для хранения сессий или данных профиля.
*   Репликация: Разделение трафика на чтение (Read Replicas) и запись.
